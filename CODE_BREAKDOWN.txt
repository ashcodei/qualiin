PLAN TYPO FINDER - CODE BREAKDOWN
=================================

This document describes each first-party code file in the project under `backend/app/` (including the `typo` package and the frontend assets), with:
- A high-level overview of what the file does.
- A list of main functions/classes and their roles.
- A line-by-line style walkthrough grouped by logical blocks.

Virtualenv / third‑party library files under `.venv/` are NOT covered here.

------------------------------------------------------------
backend/app/main.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`main.py` defines the FastAPI application that powers Plan Typo Finder. It:
- Configures the FastAPI app, static files, and session middleware.
- Serves the SPA HTML for login, signup, dashboard, and document views.
- Provides authentication endpoints (register, login, logout, “me”).
- Provides document management endpoints (uploading PDFs, listing docs, getting results, deleting docs).
- Manages the user allowlist API and triggers reprocessing when allowlist changes.

KEY FUNCTIONS / CLASSES
-----------------------
- `app = FastAPI(...)` (lines 21–22): Main FastAPI application instance with session middleware.
- `require_user(request: Request) -> str` (28–33): Dependency that enforces authentication, clearing invalid sessions.
- `_startup()` (36–40): Startup handler to initialize the DB and create a default user if configured.
- `_serve_app()` (42–43): Reads and returns `static/index.html` as a string (SPA shell).
- `index()`, `login_page()`, `signup_page()` (46–58): Route handlers that serve the SPA for root, login, and signup paths.
- `_session_user_valid(request)` (61–64): Checks if the session user still exists in the DB.
- `dashboard_page(request)` (67–72): Guards `/dashboard` and serves app or redirects to login.
- `doc_page(request, doc_id)` (75–80): Guards `/doc/{doc_id}` and serves app or redirects to login.
- `LoginBody`, `RegisterBody` (83–91): Pydantic models for auth requests.
- `_ensure_default_user()` (93–102): Creates a default user from env vars if there are no users.
- `register(body)` (106–112): `POST /api/register` - creates a new user.
- `login(request, body)` (115–123): `POST /api/login` - verifies credentials and stores user in session.
- `me(request)` (126–131): `GET /api/me` - returns current session user.
- `logout(request)` (134–137): `POST /api/logout` - clears session.
- `upload(...)` (140–164): `POST /api/upload` - legacy multi-file upload endpoint (not used by current UI, but functional).
- `create_doc(...)` (167–193): `POST /api/docs` - main “New doc” endpoint that stores metadata and enqueues processing.
- `docs_list(...)` (196–212): `GET /api/docs` - returns documents plus typo counts (if finished).
- `doc(doc_id, ...)` (215–225): `GET /api/docs/{doc_id}` - returns a single document’s state and whether result files exist.
- `delete_doc(doc_id, ...)` (228–233): `DELETE /api/docs/{doc_id}` - removes a document and associated files via jobs layer.
- `result(doc_id, ...)` (236–241): `GET /api/docs/{doc_id}/result` - returns the JSON typo analysis for a document.
- `AllowlistBody` (244–246): Pydantic model for allowlist API.
- `allowlist_get(...)` (248–251): `GET /api/allowlist` - returns user allowlist words.
- `allowlist_add(...)` (254–260): `POST /api/allowlist` - adds words to allowlist.
- `allowlist_remove(...)` (263–270): `DELETE /api/allowlist` - removes words from allowlist and reprocesses all docs.
- `reprocess(doc_id, ...)` (273–280): `POST /api/docs/{doc_id}/reprocess` - requeues processing of one doc.
- `reprocess_all(...)` (283–287): `POST /api/reprocess-all` - requeues all docs.
- `get_pdf(...)` (290–295): `GET /api/docs/{doc_id}/pdf` - returns original uploaded PDF file.
- `annotated(...)` (298–309): `GET /api/docs/{doc_id}/annotated.pdf` - returns annotated PDF (inline or as download).

  - Calls `init_db()` to ensure DB schema exists.

- 42–43: `_serve_app`:

  - `signup_page()`: returns `_serve_app()` at `/signup`.

    - Otherwise serves the SPA.
  - `doc_page(request, doc_id)`:
    - Same auth guard as dashboard.
    - Serves SPA; the JS router uses `/doc/{doc_id}` to open that document.

- 61–64: `_session_user_valid`:
  - Looks at `request.session["user"]`.
  - Returns True only if present and still in DB (`user_exists`).

  - `LoginBody`: fields `username` and `password`, defaulting to empty strings.

  - Returns immediately if login env vars are not set or a user already exists.

- 105–113: `register` (`POST /api/register`):
  - Tries to `create_user`.
  - On success returns `{ok: True, message: "..."}`
  - On `ValueError` raises `HTTPException(400)` with error string (e.g. username invalid or taken).

- 115–123: `login` (`POST /api/login`):
  - Normalizes username and password.
  - Uses `verify_user`; if that fails, raises `HTTPException(401)`.
  - On success sets `request.session["user"]` and returns `{user: session_username}`.

- 126–131: `me` (`GET /api/me`):
  - Reads user from session.
  - If missing, returns 401; otherwise returns user JSON.

- 134–137: `logout` (`POST /api/logout`):
  - Clears session and returns `{ok: True}`.

- 140–164: `upload` (`POST /api/upload`):
  - Legacy multi-file endpoint (not used by SPA but still valid).
  - Requires auth via `Depends(require_user)`.
  - Accepts `files: List[UploadFile]`.
  - Filters only `.pdf` files; for each:
    - Generates a new `doc_id`.
    - Writes file contents under `ORIG_DIR/{doc_id}.pdf`.
    - Inserts/updates document row with `status="queued"`.
    - Calls `submit_doc` to start background processing.
  - Returns array of `{"doc_id", "filename"}` for accepted PDFs.

- 167–193: `create_doc` (`POST /api/docs`):
  - Protected route (auth via `require_user`).
  - Accepts `name`, `description`, and a single `file` via form fields.
  - Validates that file is a PDF.
  - Generates `doc_id` and writes the raw PDF to disk.
  - Normalizes name/description (trimming, defaulting to filename if needed).
  - Defines nested `enqueue_doc` that calls `submit_doc(...)`.
  - Submits that function to `EXEC` (ThreadPoolExecutor) so SQLite writes happen off-request thread.
  - Returns JSON containing `doc_id`, `filename`, `name`, and `description`.

- 196–212: `docs_list` (`GET /api/docs`):
  - Requires auth.
  - Loads docs via `list_docs()`.
  - For each doc:
    - If status is `done`, tries to open the JSON result file and attach `typo_count`.

  - Returns `{"docs": docs}` for frontend to display dashboard and doc sidebar.

- 215–225: `doc` (`GET /api/docs/{doc_id}`):
  - Requires auth.

  - Uses `paths_for` to compute file paths and includes `has_result` and `has_annotated` flags.

- 228–233: `delete_doc` (`DELETE /api/docs/{doc_id}`):
  - Requires auth.
  - Calls `delete_doc_completely`; if it returns False, raises 404; else `{ok: True}`.

- 236–241: `result` (`GET /api/docs/{doc_id}/result`):
  - Requires auth.
  - Computes path to JSON result file and returns 404 if not exists.
  - Reads JSON and returns it via `JSONResponse`.

- 244–246: `AllowlistBody` model with `words: List[str]`.

- 248–251: `allowlist_get`:
  - Requires auth.
  - Uses `get_user_allowlist_words()` to retrieve user allowlist.

- 254–260: `allowlist_add`:

  - If no words, returns `{"ok": True, "added": 0}`.

- 263–270: `allowlist_remove`:
  - Requires auth.
  - If no words, returns `{"ok": True, "removed": 0}`.

- 273–280: `reprocess`:

- 283–287: `reprocess_all`:

  - Calls `reprocess_all_docs()`; returns how many docs were queued.

- 290–295: `get_pdf` (`GET /api/docs/{doc_id}/pdf`):

  - Returns original PDF file.

- 298–309: `annotated` (`GET /api/docs/{doc_id}/annotated.pdf`):

  - Serves annotated PDF inline or as an attachment depending on `download` flag.

backend/app/db.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`db.py` provides a small data-access layer built around SQLite. It:
- Creates and migrates the `documents` and `users` tables.
- Manages user creation and credential verification (with salted PBKDF2 hashing).
- Exposes CRUD functions for documents (insert/update, list, get, delete).

KEY FUNCTIONS / CLASSES
-----------------------
- `DB_PATH` (8): Points to `backend/app/storage/app.db`.
- `init_db()` (10–40): Creates DB file/directories and ensures tables/columns exist.
- `_hash_password(password, salt)` (43–44): PBKDF2-HMAC-SHA256 password hashing helper.
- `create_user(username, password)` (47–67): Validates and inserts a new user, raising if invalid or duplicate.
- `get_user_by_username(username)` (70–79): Looks up a user row and returns `(user_id, username, password_hash, salt_hex)` or `None`.
- `verify_user(username, password)` (82–95): Verifies credentials and returns username if correct.
- `has_any_user()` (98–101): True if DB has at least one user.
- `user_exists(username)` (104–109): True if username exists.
- `upsert_doc(...)` (112–136): Inserts or updates a document row with filename, status, progress, etc.
- `get_doc(doc_id)` (138–142): Returns document row as dict or `None`.
- `list_docs()` (144–148): Returns list of documents ordered by creation time.
- `delete_doc(doc_id)` (151–156): Deletes document row; returns True if a row was deleted.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–7: Imports: `hashlib`, `secrets`, `sqlite3`, `Path`, typing.
- 8: `DB_PATH` is set to `<this dir>/storage/app.db`.

- 10–40: `init_db`:
  - 11: Ensures DB directory exists.
  - 12–31: Opens a connection and runs `CREATE TABLE IF NOT EXISTS` for:
    - `documents` with `doc_id`, `filename`, `status`, `progress`, `message`, timestamps.
    - `users` with `user_id`, `username`, `password_hash`, `salt`, `created_at`.
  - 32–40: Migration logic for adding `name` and `description` columns to `documents` if missing.

- 43–44: `_hash_password`:
  - Uses `hashlib.pbkdf2_hmac` with 100k iterations, returning the hex string.

- 47–67: `create_user`:
  - Normalizes/validates username and password length.
  - Generates 32-byte random salt and hashed password.
  - Generates a random `user_id` (`secrets.token_hex(16)`).
  - Inserts into `users` table with timestamp.
  - On duplicate username, translates `sqlite3.IntegrityError` to `ValueError("Username already taken")`.

- 70–79: `get_user_by_username`:
  - Executes SELECT query filtering by normalized username.
  - Returns tuple if found, `None` otherwise.

- 82–95: `verify_user`:
  - Looks up username, retrieving stored hash and salt hex.
  - Recomputes hash for given password and compares.
  - Returns stored username if match, else `None`.

- 98–101: `has_any_user`:
  - Simple check using `SELECT 1 FROM users LIMIT 1`.

- 104–109: `user_exists`:
  - Similar to above but checks for specific username.

- 112–136: `upsert_doc`:
  - Accepts doc identifiers/status plus optional `name` and `description`.
  - Gets current time, then uses an `INSERT ... ON CONFLICT(doc_id) DO UPDATE` statement to:
    - Insert new docs.
    - Update status/progress/message/filename on existing docs, while:
      - Only overwriting `name` when non-empty in the new row.
      - Overwriting `description` only when non-None (allows clearing).

- 138–142: `get_doc`:
  - Reads a single `documents` row, using `sqlite3.Row` for dict-style access and converting to dict.

- 144–148: `list_docs`:
  - SELECTs all docs ordered by `created_at DESC`.

- 151–156: `delete_doc`:
  - Deletes row by `doc_id`.
  - Returns boolean depending on `rowcount`.

backend/app/jobs.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`jobs.py` manages background processing of PDFs:
- Defines storage paths for original, annotated, and result files.
- Sets up a global `ThreadPoolExecutor` for parallel PDF typo scanning.
- Wraps `process_pdf` from `processor.py` with progress reporting.
- Provides functions to submit/requeue jobs, list document-related paths, and manage a user allowlist file.

KEY FUNCTIONS / CONSTANTS
-------------------------
- `STORAGE`, `ORIG_DIR`, `ANN_DIR`, `RES_DIR`, `DATA_DIR` (10–15): Project-relative directories for all artifacts.
- `MAX_WORKERS`, `EXEC` (24–25): Thread pool configuration for job concurrency.
- `_progress_cb(...)` (27–51): Internal helper that writes progress updates to the DB.
- `submit_doc(...)` (53–63, 68–103): Enqueues a new PDF processing job in thread pool.
- `reprocess_doc(doc_id)` (106–120): Re-enqueues processing for an existing document if source exists.
- `reprocess_all_docs()` (123–138): Iterates all docs and requeues those with existing original files.
- `paths_for(doc_id)` (141–146): Returns paths to original, annotated, and result files for a doc.
- `delete_doc_completely(doc_id)` (149–165): Deletes DB row and all artifact files, including error logs.
- `USER_ALLOWLIST_PATH` (168–169): Path to `user_allowlist.txt` in `data` dir.
- `add_to_user_allowlist(words, prepend=False)` (171–198): Inserts new words to the allowlist file.
- `get_user_allowlist_words()` (201–210): Reads allowlist file into a list.
- `remove_from_user_allowlist(words_to_remove)` (213–224): Removes given words from allowlist file.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–5: Imports for future annotations, OS/time/traceback, `ThreadPoolExecutor`, `Path`, and typing.
- 7–8: Import DB helpers and `process_pdf`.
- 10–15: Setup of filesystem directories relative to this module.
- 16–18: Ensure original, annotated, and result directories exist.

- 20–25: ThreadPoolExecutor config:
  - Comment explains why threads are used (SQLite view sharing on Windows).
  - `MAX_WORKERS` capps at 4 CPUs.
  - `EXEC` is a global `ThreadPoolExecutor`.

- 27–51: `_progress_cb`:
  - Accepts `doc_id`, page counts, a note, optional `pct`, plus filename/name/description.
  - Computes `progress` either from `pct` (clamped to 0–99) or from pages done/total.
  - Calls `upsert_doc` to update DB status to `"processing"`, saving message and metadata.

- 53–63: `submit_doc` signature:
  - Accepts IDs, filename, input path, and optional name/description.
  - First calls `upsert_doc` to mark doc as `"queued"`.

- 65–100: `_run` inner function:
  - 70–73: Immediately sets status to `"processing"` and progress 0.
  - 75–77: Defines `progress_cb` that wraps `_progress_cb` with filename/name/description for this doc.
  - 78–85: Calls `process_pdf` from `processor.py` with `DATA_DIR` and `progress_cb`.
  - 86–90: On success, updates doc row to `"done"`, progress 100, and sets `message` to `typos=<count>`.
  - 92–100: On exception:
    - Writes stack trace to `RES_DIR/{doc_id}.error.txt`.
    - Marks doc as `"failed"` with message set to exception string.
    - Raises the error again so callers can inspect.

- 102–103: Schedules `_run` via `EXEC.submit` and returns the `Future`.

- 106–120: `reprocess_doc`:
  - Uses `get_doc` to ensure the doc exists.
  - Asserts the original file path exists, else raises `FileNotFoundError`.
  - Calls `submit_doc` with the same filename/name/description as stored in the DB.

- 123–138: `reprocess_all_docs`:
  - Loops all docs from DB.
  - Skips those without `doc_id` or original file.
  - Calls `reprocess_doc` for each and counts how many were queued, ignoring missing-file errors.

- 141–146: `paths_for`:
  - Returns a mapping of logical names (`original`, `annotated`, `result`) to actual Paths.

- 149–165: `delete_doc_completely`:
  - Iterates the known file types and tries to delete them if they exist.
  - Also deletes `.error.txt` log if present.
  - Calls `db_delete_doc` to remove the DB row.
  - Returns True when underlying DB delete removed a row.

- 168–169: `USER_ALLOWLIST_PATH` points to `data/user_allowlist.txt`.

- 171–199: `add_to_user_allowlist`:
  - Normalizes input words (strip, lower).
  - Deduplicates while preserving order.
  - Loads any existing lines and builds a set of existing words (ignoring comments/blank lines).
  - Calculates `to_add` as words not already present.
  - If `prepend=True`:
    - Writes new words at top and keeps existing non-duplicate lines after them.
  - Else:
    - Appends new words to the file.

- 201–210: `get_user_allowlist_words`:
  - If file absent, returns `[]`.
  - Splits lines, strips, ignores blanks and comment lines, returns list.

- 213–224: `remove_from_user_allowlist`:
  - Normalizes removal words, builds case-insensitive remove set.
  - Reads file; keeps only lines whose normalized form is not in remove set.
  - Writes updated contents back to file.

backend/app/processor.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`processor.py` encapsulates the core PDF processing pipeline:
- Opens a PDF with PyMuPDF, examines each page’s text, and identifies typo candidates.
- Applies several filters, spell checking, and optional Ollama-based context validation.
- Draws red rectangles around detected typos on a copy of the PDF (annotated version).
- Produces a JSON result file with typo metadata, page dimensions, and summary stats.

KEY FUNCTIONS / CLASSES
-----------------------
- `TypoHit` dataclass (13–21): Represents one detected typo instance, including PDF coordinates and context.
- `_group_words_into_lines(words)` (22–30): Groups raw PyMuPDF `get_text("words")` output into line-based structures.
- `_line_text(line_words)` (32–33): Builds text string from a list of word entries.
- `process_pdf(doc_id, in_pdf, out_pdf, out_json, data_dir, progress_cb=None)` (35–198): The main pipeline for scanning typos, annotating PDF, and emitting JSON.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–5: Import future annotations, JSON/time, dataclasses, Path, and generics.
- 7: Import `fitz` (PyMuPDF) for PDF operations.
- 9–11: Import filter config/helpers (`FilterConfig`, `is_candidate`, `should_skip_before_ollama`), `SpellChecker` utilities, and `is_typo_with_context` from `ollama_check`.

- 13–21: `TypoHit`:
  - Fields:
    - `page`: 1-based page number.
    - `word`: raw word string.
    - `bbox`: PyMuPDF display bbox `[x0, y0, x1, y1]` (top-left origin).
    - `bbox_pts`: PDF points `[left, bottom, right, top]` for viewer-stable coordinates.
    - `context`: optional line-level context string.
    - `suggestions`: optional list of alternative spellings.

- 22–30: `_group_words_into_lines`:
  - Expects list of PyMuPDF word tuples `(x0, y0, x1, y1, word, block_no, line_no, word_no)`.
  - Groups them by `(block_no, line_no)` key.
  - Each line list is sorted by `x0` to preserve reading order.

- 32–33: `_line_text`:
  - Concatenates the `word` entries (element 4) with spaces to form a line string.

- 35–43: `process_pdf` docstring and initial `start` time capture.
  - Explains that progress is mapped into ranges (0–5, 5–95, 95–99, 100).

- 46–52: Phase 1: global setup:
  - Notifies progress callback (if provided) at 1% with “Loading allowlists…”.
  - Loads allowlists (abbrev + domain) from `data_dir`.
  - Creates `SpellChecker` and default `FilterConfig`.

- 53–59: 2nd progress callback at 3% (“Opening PDF…”), open PDF with `fitz.open`, compute `total_pages`, initialize `hits` list and `page_dimensions` dict.

- 60–65: `page_progress` helper:
  - Translates in-page fraction (0–1) into global 5–95 band across pages so progress appears smooth.

- 68–70: Notes on annotation strategy (modify copy of doc; save at end).

- 70–165: Main per-page loop (`for pi in range(total_pages)`):
  - 71–72: Compute `page_num` and load page.
  - 75–78: Progress callback for “Reading page…”.
  - 79–80: Call `page.get_text("words")`.
  - 80–85: If there’s no text layer or too few words, treat as “no text layer” and skip deeper processing, but still advance page progress.

  - 87–95: Build line/group structures:
    - 88–90: Progress callback for “Extracting text on page…”.
    - 92: Build `lines` via `_group_words_into_lines`.
    - 94: Build `line_strs` (a dict from `(block, line)` to string line) for context.

  - 96–101: Compute page geometry:
    - Use `page.cropbox` or fallback to `page.rect`.
    - Store width/height/page_box into `page_dimensions[page_num]`.

  - 103–107: Setup for within-page progress:
    - `total_words`, a list of milestone fractions `[0.35, 0.55, 0.75, 0.95]`.
    - `milestone_idx` indexes into these.

  - 108–159: Iterate each word `w` on page:
    - 109–110: Unpack word tuple; `raw = txt`.
    - 111–116: Run candidate filtering and spell checks:
      - If `is_candidate` fails or `spell.is_allowed` or `spell.is_valid`, skip.
    - 118–122: If not allowed/valid:
      - If `should_skip_before_ollama(raw)` returns True, skip (treat as abbreviation).
      - Determine `ctx` from `line_strs`.
      - Use `is_typo_with_context(raw, ctx)` to optionally consult Ollama; skip if model says NOT a typo.
    - 124–137: For confirmed typos:
      - Compute `bbox_pts` in PDF points coordinates.
      - Call `spell.suggestions` to get domain-based candidates.
      - Create a `TypoHit` with context and suggestions, append to `hits`.
      - 141–143: Draw a padded red rectangle on PDF page around the word.

    - 145–159: Progress within page:
      - Compute `frac_done` as portion of words processed.
      - For each milestone crossed, call `page_progress` and emit a status update like “Scanning for typos…”.

  - 161–164: After finishing the page, ensure progress for that page slice reaches near the end of its band.

- 166–170: Phase 3: saving outputs:
  - Notifies progress at 96% (“Saving annotated PDF…”).
  - Ensures output directories exist.
  - Saves annotated PDF to `out_pdf` (with garbage collection/deflate) and closes document.

- 174–186: Writes JSON:
  - Another progress update at 99% (“Writing result data…”).
  - Ensures `page_dimensions` entries for every page (including pages with no text) by reloading page rects if missing.

- 188–197: Build `payload`:
  - Includes runtime (seconds), doc id, `page_dimensions`, `typo_count`, full `typos` list (`asdict(h)` for each `TypoHit`), and plan identifier.
  - Writes `payload` to `out_json` with indentation.
  - Returns `payload` for callers (such as jobs layer).

backend/app/typo/spell.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`spell.py` encapsulates spell-check logic and allowlists:
- Wraps `pyenchant` (via `enchant.Dict`) to check for valid English words.
- Uses Zipf frequency (`wordfreq`) as a fallback for words not in the dictionary.
- Provides suggestion generation based on a limited “domain” word pool with `rapidfuzz`.
- Loads abbreviation and domain allowlists (plus per-user allowlist) from text files.

KEY FUNCTIONS / CLASSES
-----------------------
- `SpellConfig` dataclass (9–16): Tuning options such as Zipf threshold, number of suggestions, score threshold.
- `SpellChecker` class (17–68):
  - `__init__(abbrev_allow, domain_allow, cfg=None)`:
    - Stores abbreviation and domain allowlists.
    - Initializes `enchant.Dict("en_US")`.
    - Builds `suggestion_pool` as sorted domain allowlist.
  - `_clean_for_lookup(t)` (29–31): Lowercases and strips whitespace.
  - `is_allowed(raw)` (33–37): Checks if word is in abbreviation allowlist (e.g., all-caps engineering abbreviations).
  - `is_valid(raw)` (39–59): Main validity check:
    - Rejects empty tokens.
    - Accepts abbreviations (abbrev allowlist) or domain terms (domain allowlist).
    - Checks enchant dictionary; if word is valid English, returns True.
    - Handles possessive `'s` by checking base word as well.
    - Falls back to `zipf_frequency` from `wordfreq` with `zipf_threshold` to catch very common words not in dictionary.
  - `suggestions(raw)` (61–68):
    - If suggestion pool is empty, returns [].
    - Looks up candidates from `suggestion_pool` via `rapidfuzz.process.extract`.
    - Filters by `suggestion_min_score` and returns up to `max_suggestions`.
- `load_allowlists(data_dir)` (70–85):
  - Loads abbreviation allowlist from `abbrev_allowlist.txt`.
  - Loads domain allowlist from `domain_allowlist.txt`.
  - Also merges in user allowlist (`user_allowlist.txt`), lowercased, into domain set.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–8: Imports, dataclasses, `Path`, typing, `wordfreq.zipf_frequency`, `rapidfuzz`, and `enchant`.

- 9–16: `SpellConfig`:
  - `zipf_threshold`: baseline log-frequency threshold for lexicon acceptance.
  - `max_suggestions`: how many suggestions to return.
  - `suggestion_min_score`: minimum rapidfuzz similarity (0–100).

- 17–28: `SpellChecker.__init__`:
  - Normalizes abbreviation allowlist to raw strings (stripping).
  - Lowercases domain allowlist.
  - Uses passed config or default.
  - Builds `self._dict` with `en_US`.
  - Builds `suggestion_pool` as sorted domain terms (list).

- 29–31: `_clean_for_lookup`:
  - Utility: strip and lower-case word for dictionary/Zipf lookups.

- 33–37: `is_allowed`:
  - Checks raw word membership in `abbrev_allow` set.
  - Returns True if found; else False (the comment explains that all-caps tokens are handled only here).

- 39–59: `is_valid`:
  - Quick path for empty words or abbreviations.
  - Normalizes to `low` via `_clean_for_lookup`.
  - Checks domain allowlist; if present, valid.
  - Checks dictionary; if yes, valid.
  - Additional rule for `low.endswith("'s")`: tests base word in dictionary.
  - If still not accepted, uses `zipf_frequency(low, "en")` vs threshold; if above threshold, treat as valid.
  - Otherwise returns False (typo candidate).

- 61–68: `suggestions`:
  - If `suggestion_pool` is empty, returns [].
  - Lowercases input and finds matches with `rapidfuzz`.
  - Filters suggestions by `suggestion_min_score`.

- 70–85: `load_allowlists`:
  - Builds `abbrev` and `domain` sets.
  - Reads `abbrev_allowlist.txt` and `domain_allowlist.txt`, skipping comments / blank lines.
  - Reads `user_allowlist.txt` if present and merges each non-comment line (lowercased) into `domain`.
  - Returns `(abbrev, domain)` for pipeline initialization.

backend/app/typo/filters.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`filters.py` defines heuristic rules for which tokens should be considered typo candidates:
- Uses regexes to ignore obvious non-words like pure numbers, dimension strings, sheet references, and alphanumeric labels.
- Enforces minimum alphabetic length and other structural requirements.
- Contains a helper to skip certain words before calling Ollama (e.g., tokens with special characters).

KEY FUNCTIONS / CLASSES
-----------------------
- Compiled regexes (5–10): For numbers, dimensions, sheet labels, mixed alphanumeric, and pure punctuation.
- `_ALLOWED_CHARS` (12–14): White-list of characters allowed before calling Ollama.
- `FilterConfig` dataclass (15–20): Tunable thresholds like minimum alpha length and max token length.
- `normalize_token(t)` (21–25): Helper to strip edge punctuation (not heavily used in pipeline).
- `is_candidate(t, cfg)` (27–54): Decides if token should be passed to spell-check pipeline.
- `should_skip_before_ollama(word)` (57–75): Heuristics for skipping calls to Ollama for certain tokens.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–4: Imports for annotations, regex, dataclasses.
- 5–10: Regex definitions:
  - `RE_PURE_NUM`: integers or decimals only.
  - `RE_DIM`: dimension expressions like `12'` or `12"`.
  - `RE_SHEET`: sheet identifiers like `C3.3` or `A1`.
  - `RE_ALNUM`: tokens containing both letters and digits.
  - `RE_PUNCT`: pure punctuation and underscore.

- 12–14: `_ALLOWED_CHARS`:
  - Character set that is accepted before sending to Ollama; everything else indicates we should skip the call.

- 15–20: `FilterConfig`:
  - Adds shape constraints (min alpha len, allowed all-caps, max token len).

- 21–25: `normalize_token`:
  - Trims whitespace around token and strips leading/trailing non-alphanumeric characters.

- 27–54: `is_candidate`:
  - Returns False for:
    - Empty tokens.
    - Tokens longer than `max_token_len`.
    - Pure punctuation or numeric/dimension patterns.
    - Sheet refs and mixed alphanumeric codes.
    - Single-letter tokens or 2-letter all-caps (likely compass directions / codes).
    - Tokens with no alphabetic characters.
    - Tokens whose alphabetic-only string is shorter than `min_alpha_len`.
  - Only tokens that survive all checks are considered for further typo detection.

- 57–75: `should_skip_before_ollama`:
  - Returns True (skip calling Ollama) if:
    - Word is empty.
    - Contains any dot (`.`), slash (`/` or `\`), or characters outside `_ALLOWED_CHARS`.
  - This marks tokens to be treated as abbreviations or special tokens that the LLM shouldn’t evaluate.

backend/app/typo/ollama_check.py
------------------------------------------------------------

GENERAL OVERVIEW
----------------
`ollama_check.py` implements an optional LLM-based typo verification step using Ollama:
- Reads environment configuration for whether to enable the check, which model to call, and connection settings.
- Builds a carefully worded prompt describing what counts as a typo vs an abbreviation in engineering plans.
- Calls the Ollama HTTP API (`/api/generate`) and interprets YES/NO responses.
- Integrates with pipeline by exposing `is_typo_with_context`.

KEY FUNCTIONS / CONSTANTS
-------------------------
- `OLLAMA_ENABLED`, `OLLAMA_MODEL`, `OLLAMA_URL`, `OLLAMA_TIMEOUT`, `OLLAMA_MAX_TOKENS` (13–18): Config knobs from environment.
- `_call_ollama(prompt)` (21–38): Handles HTTP POST to Ollama to get a response text.
- `is_typo_with_context(word, context)` (42–95): Core helper that returns True if a word should be treated as a typo.

LINE-BY-LINE / BLOCK WALKTHROUGH
--------------------------------
- 1–4: Module docstring explains purpose, with recommended models.
- 5–11: Imports (`json`, `os`, `re`, `urllib`, `Optional`).
- 13–18: Environment flags:
  - `OLLAMA_ENABLED` decides whether to *actually* call Ollama.
  - `OLLAMA_MODEL` default is `llama3.2:3b`.
  - `OLLAMA_URL`, timeout, and `OLLAMA_MAX_TOKENS` (response length).

- 21–38: `_call_ollama`:
  - 23–28: Builds JSON body containing `model`, `prompt`, `stream=False`, and generation options.
  - 29–34: Creates HTTP request to `OLLAMA_URL/api/generate`.
  - 35–37: Sends request with timeout and parses JSON response, returning `.response` field.
  - 38–39: Catches network/HTTP/JSON errors and returns `None` (treated as error).

- 42–50: `is_typo_with_context` control flow:
  - If Ollama is disabled (`OLLAMA_ENABLED` False), returns True immediately so pipeline relies solely on spell check.
  - Assembles `sentence` from `context` or falls back to word.
  - If word is empty, treat as typo (True).

- 56–77: Prompt construction:
  - Multi-line string clearly defines conditions when to answer YES vs NO.
  - Emphasizes that partial spellings and phonetic spellings should be considered typos.
  - Instructs model to reply exactly “YES” or “NO”.
  - Embeds the sentence and the word.

- 78–80: Calls `_call_ollama`; on error, treats as typo (True).

- 82–90: Response normalization:
  - Compresses whitespace and uppercases the response.
  - If output looks like an instruction echo (includes “RULE:” etc.), treat as typo (YES) for safety.
  - Splits first word; if first word is “NO” and total string length is small, log and return False (not a typo).

- 93–95: Otherwise logs debug and returns True (treat as typo).
